# 课程生成器产品需求文档

> 版本：v0.2（需求基线）  
> 状态：V1 需求基线已确认  
> 日期：2026-09-07  
> 产品名称：课程生成器

## 1. 产品概述

本产品面向经常借助 AI 学习新知识的自学者，将重复发生的“明确需求、规划课程、查找资料、生成正文、审校、返工和发布”过程固化为一个可观察、可暂停、可恢复、有人类把关的课程生产工作流。

产品不以聊天作为主操作方式。用户主要通过结构化表单、可编辑产物、阶段状态和审核动作推进课程生成。

课程正文的唯一事实源是 Markdown。HTML 是由已批准 Markdown 构建的发布视图，不允许直接编辑。

## 2. 产品目标

### 2.1 核心目标

- 把模糊的学习想法转化为可验收的课程任务。
- 自动完成资料收集、课程规划、逐章生成和多层质量检查。
- 在关键节点让人工拥有批准、要求返工和停止三种权力。
- 保证每个中间产物可以追溯，每次人工决定可以恢复。
- 记录每次模型调用实际消耗的 Token，并能关联到课程、阶段、节点和产物。
- 生成可阅读、可下载、可验证的 Markdown 课程与静态 HTML 课程站点。

### 2.2 V1 非目标

- 不提供多用户、登录、团队权限或在线协作。
- 不支持音频、视频、图片和上传文件作为来源。
- 不建设复杂的向量数据库或大规模 RAG 平台。
- 不建设可视化 Prompt 管理后台。
- 不自动部署到 CDN、云平台或自定义域名。
- 不承诺并行生成章节；仅预留未来并行能力。
- 不支持登录网页、付费墙、整站爬取和复杂动态页面抓取。
- 不接入邮件、短信、Webhook 或桌面通知。
- 不支持从界面永久删除课程，也不支持导入工作区后恢复流程。

## 3. 目标用户与主要场景

### 3.1 V1 目标用户

以个人自学者为主。用户希望围绕一个新主题快速获得结构清晰、来源可追溯、经过质量闭环的系统课程，而不是重复与通用聊天机器人进行相同的需求确认和写作对话。

### 3.2 核心使用路径

1. 用户填写课程名称、受众、学习目标、内容范围等要求。
2. 系统将要求固化为可验收任务。
3. 系统处理用户资料，并按来源政策联网检索补充资料。
4. 系统生成课程蓝图和批次计划，交由用户审核。
5. 系统逐批、逐章生成课程并完成质量闭环。
6. 系统进行整课回归和一致性修复。
7. 用户确认发布候选，系统生成正式交付包并由用户做最终发布决定。

## 4. 产品原则

### 4.1 系统与模型职责

系统代码负责：

- 工作流顺序、节点路由和阶段状态。
- 权限、预算、停止条件和人工中断。
- 文件写入、数据库持久化、版本、哈希与并发控制。
- 确定性校验、质量门通过条件、重试上限和失效恢复。
- 来源政策、发布候选与发布包管理。

模型只在需要理解、规划、写作、语言优化和语义审校的节点工作。模型不得自行写文件、修改数据库、提升预算、批准产物、改变来源政策或决定发布。

### 4.2 人工控制

在阶段审核和异常升级位置，人工拥有：

- 批准：确认当前产物并进入下一阶段。
- 要求返工：提交目标、意见或反驳证据，返回相应修复入口。
- 停止：停止当前课程运行，保留已有状态和产物。

人工不能在普通批准动作中直接豁免真实 blocker。人工可提交证据反驳 blocker；证据成立时标记为不成立。规则修改必须作为受控变更记录，并作用于后续调用。

## 5. 用户可见的七个阶段

七个阶段用于前端展示课程进度，不与 LangGraph 节点一一对应。每个阶段可以由多个节点、子图、条件分支和人工中断组成。

### 阶段一：课程需求

输入字段：

- 课程名称。
- 目标受众。
- 学习目标。
- 内容范围。
- 期望章节数。
- 单章有效字符数下限。
- 是否限制 Token；启用时填写阈值。
- 来源政策。
- 补充课程资源：网页 URL 或直接粘贴文本。

必填项缺失或格式无效时必须停下来询问用户。模型可以提出补全建议，但不能静默替用户确定。

产物：结构化课程输入、原始输入快照、缺失项与风险清单。

### 阶段二：任务定义

将“想做一门课”改写为可验收任务，明确：

- 为什么存在这门课。
- 面向谁学习。
- 学完解决什么问题。
- 学习者用什么结果证明已经学会。
- 必须讲、可选讲和禁止讲的内容。
- 来源政策。
- 章节、篇幅、Token 和交付要求。
- 课程验收标准。

学习目标原则上为 3–7 条可观察目标。每章应包含与目标关联的练习；课程主题适合时增加一个综合练习。

产物：`MISSION.md`、`SPEC.md`。

### 阶段三：来源与课程蓝图

先处理用户资料并按来源政策自动联网检索，再生成课程蓝图。只有出现关键资料缺失、来源冲突或政策不满足时提前中断；正常情况下在来源和蓝图生成完成后统一交由人工审核。

蓝图至少描述：

- 模块目标及其章节。
- 每章标题、核心问题和学习目标。
- 必须覆盖的内容、示例和练习。
- 计划使用的来源。
- 与前后章节的衔接。
- 预计章节体量。

预计章节体量仅为规划目标或估算，不能作为阶段五的实际篇幅验收值。

退出检查包括：学习目标覆盖、章节与目标对应、先修关系、范围约束、来源合规和预算级可行性。

产物：`RESOURCES.md`、`BLUEPRINT.md`、章节到来源的依赖索引。

### 阶段四：批次规划

系统沿模块边界将章节划分为连续批次。批次大小可单独配置；预计体量过大的章节可以单独成批。

每批记录：

- 批次标识和章节范围。
- 划分理由。
- 预计字符数。
- Context Pack 引用范围。
- Token 预算。
- 顺序与停止条件。

V1 默认按顺序执行。只有依赖声明足以证明章节之间无内容依赖时才允许并发；无法确定时必须顺序执行，并发仅作为预留能力。

`context_pack_scope` 必须由对蓝图章节、工作区文件和来源片段的可解析引用组成，不能只有自由文本。

阶段四只生成批次计划，禁止提前生成 Context Pack 文件。

退出校验：

- 每章恰好属于一个批次。
- 章节顺序正确。
- 不无故跨越模块边界。
- 各批预算总量可行，且不存在明显超预算单章。
- Context Pack 范围引用完整。
- 工作区不存在阶段四提前生成的 Context Pack。
- 人工批准批次、执行顺序和预算。

产物：`workspace/batches/<batch-id>.json`。

### 阶段五：批次生产循环

批次是人工确认和交付单位，章节是生成、检查和修复单位。一个批次的所有章节没有全部通过时，该批次不算完成。

每次正文生成调用只写一章。批内章节默认串行执行；批次级连续性审查只读，不直接修改正文。

单章流程：

```text
生成 Context Pack
→ 首次正文生成或定向修复
→ 确定性预检
→ Humanizer
→ 确定性回归
→ 语义审校
→ 三门汇总
```

预检失败直接返回写入或修复步骤，不进入 Humanizer 和语义审校。语义修改后的片段必须重新经过 Humanizer 和确定性回归，保证审校面对的是最终文本。

#### 自动返工预算

- 一轮指生成一份章节候选，并走到完整质量门汇总；一次模型调用或一次网络重试不单独算一轮。
- 每章最多 3 轮自动生成或定向修复。
- 同一 blocker 指纹连续出现 2 轮时提前转人工。
- 各轮问题不同但累计 3 轮仍失败时转人工。
- blocker 指纹由规则、逻辑位置和证据版本哈希构成。
- 3 轮是自动预算；人工提供新的定向意见或证据后可重置计数，但历史必须保留。
- 内层单章单任务上限与外层整课质量闭环总闸分别计数和管理。

#### 章节冻结

通过三门后冻结的是当前批次通过质量门的那个 Markdown 版本。后续普通流程不能修改；若后续批次或整课审查出现新证据，或人工主动发起修改，可以重开章节，重开后必须重新通过受影响的质量门。

产物：逐章 Markdown、Context Pack、质量结果、连续性记录和批次结果。

### 阶段六：整课质量闭环

所有批次完成后执行：

- 全课程确定性检查。
- 整课语义与教学一致性审查。
- 术语、先修关系、重复内容和章节衔接检查。
- 汇总各批遗留 warning 和未解决问题。

整课审查不得旁路章节流程直接改写语言或正文。所有正文变更必须回到相应章节的有界修复循环。

修复采用分层启动：

- 根因清晰、仅影响单章且不涉及结构、政策或传播范围的问题，可自动进入有界返工。
- 跨章、多章或根因不明的问题，先生成修复计划交人工确认。

修复计划必须包含根因、目标章节及顺序、传播范围、需要重跑的质量门。计划经确认后，各章自行进入有界返工，不再逐章要求人工批准，除非达到预算、Token 或错误上限。

修复计划只有两种合法关闭语义：修复验证通过，或人工提交证据并判定问题不成立。不得通过关闭计划绕过真实 blocker。

未解决 warning 的人工知悉必须与进入阶段七的确认动作绑定，并记录为同一个审核事件。

### 阶段七：整课确认与发布

系统生成只读 Release Candidate（RC），绑定全部可见事实源：

- `course.json`。
- 课程 Markdown。
- 术语与参考资料。
- 已批准的来源快照。
- HTML 渲染器和页面模板。

RC 记录各输入和产物的 SHA-256。任何绑定哈希变化都会使 RC 失效。

RC 失效后：

- 作废当前 RC，但保留为只读历史记录。
- 重建整套 HTML 并执行全量确定性检查。
- 语言门和语义门只对真正失效的章节重跑。
- 人工“要求返工”携带目标和意见返回阶段六修复入口，不在 RC 上直接编辑。

发布只是将仍然有效的 RC 提升为正式发布状态，不能改变包内任何字节。最终发布决定始终由人工做出。

## 6. 来源政策与联网检索

支持四种来源政策：

1. 用户资料 + 官方资料：以用户内容为基础，联网补充官方来源。
2. 仅内部材料：禁止联网搜索，只使用用户提供内容。
3. 仅公开官方资料：只接受官方或第一方公开来源。
4. 扩展资料并交叉核验：允许可信第三方来源，重要结论尽量以两个独立来源交叉确认。

联网搜索只产生候选。搜索结果摘要不能直接作为事实依据；只有抓取成功、形成正文快照并符合来源政策的页面才能被引用。

V1 来源处理保持轻量：

- URL 抓取一次并保存正文快照、抓取时间和哈希。
- 用户主动重新抓取时创建新版本，不自动监控网页变化。
- 抓取失败时允许重试、删除来源或改为粘贴文本。
- 内容哈希相同的来源视为重复。
- 优先按标题和段落切分，过长段落再按长度拆分。
- 每个片段保留临时引用及原文位置。
- 不使用向量数据库；阶段三建立章节到来源片段的映射。

具体实现采用 Tavily Search API 发现候选 URL，使用 HTTPX 重新抓取选中的页面，再使用 Trafilatura 提取主要正文。Tavily 返回的 AI 答案或搜索摘要不能作为课程事实来源。`TAVILY_API_KEY` 为可选的服务端环境变量；未配置时保留用户 URL 与粘贴文本能力，但关闭自动搜索。

抓取服务只允许 HTTP/HTTPS，禁止访问本机和内网地址，并限制响应大小和超时时间。

## 7. Context Pack

Context Pack 是阶段五由系统根据已批准产物确定性组装的单章模型输入，不是模型自由总结出的上下文。

组装顺序：

```text
通用模型约束
+ 可选通用 Skill
+ 当前节点业务提示词
+ 本章 Context Pack
+ 代码指定的输出 Schema
```

每章当前 Context Pack 保存为：

```text
workspace/context-packs/<batch-id>/chapter-<NN>.json
```

内容限于本章目标和验收要求、本章蓝图、允许来源片段、必要的前文摘要与术语、写作约束。

模型只能消费 Context Pack，不能生成、修改或自行扩大其来源范围。蓝图或来源变化导致 Context Pack 失效时创建新 revision。定向返工基于原 Context Pack 追加当前正文和质量证据，不为每次调用复制完整文件。

## 8. 质量门

章节通过必须同时满足确定性门、语言门和语义门；三门记录统一按 `{gate, hash, revision}` 保存，正文或相关事实源哈希不匹配即失效。

### 8.1 确定性门

至少检查：Markdown 结构、必要章节元素、有效字符数、引用格式、来源引用可解析性、禁止项以及构建可用性。

#### 有效字符规则

- 使用 Markdown AST 解析可见正文，不使用正则作为主实现。
- 中文、英文字母和数字计入；标点、语法符号、空白和 URL 不计。
- 代码块不计。
- Markdown 链接只计算可见标签，不计算 URL。
- 承载课程正文的引用块文字计入。
- 固定 `## 本章来源` 标题后的章末来源列表不计。
- Humanizer 后重新计算。
- 最终字符结果绑定语义审校通过的 Markdown 哈希。
- 字符数达标只表示篇幅门通过；重复填充和无效内容由语义门拦截。

### 8.2 语言门

Humanizer 节点是唯一语言门。语义审校不重复进行语言评分。

语言门采用四个等权维度：自然度、清晰度、简洁度、具体教学感。每维满分 100，单维不低于 85，综合分不低于 90，且不存在语言 blocker 时通过。

所有维度必须定义行为化锚点：90–100 优秀、85–89 可接受、70–84 需修、低于 70 为严重问题。评分由锚点映射，不允许裸估。每项扣分和 blocker 必须给出文本位置、片段、原因及修复方向。

语言 blocker 独立于分数，包括提示词或聊天残留、机械模板句、严重翻译腔或断裂表达、重复填充、表达影响理解、捏造个人身份或感受并造成不可信感。事实性虚构由语义门核验，同一问题不得双罚。

Humanizer 只处理变化的散文片段。纯结构修改或散文哈希不变时 no-op，并沿用原语言分。人工编写的散文默认只给审阅和建议，除非用户明确授权，否则不自动覆盖。

### 8.3 语义门

语义门不设数字总分，按四个维度输出 pass、warning 或 blocker：

- 事实与来源。
- 目标与范围。
- 教学有效性。
- 逻辑与连续性。

目标与范围只判断覆盖和排除；教学有效性只判断讲解与证据质量。同一缺陷不得在两个维度分别登记 blocker。

本章内部一致性问题属于本章 blocker。跨章矛盾只作为 warning 写入连续性记录，由批次或整课审查决定是否重开其他章节。

语义审校遇到“内容正确但表达已影响理解”时，可以提供路由建议，但不产生第二份语言评分。最终是否回到 Humanizer 由系统决定。

## 9. 批次审核与影响传播

批次审核前执行只读连续性检查，关注章节衔接、术语一致性、重复、先修关系和遗留 warning。

人工要求返工时，受影响范围由“人工指定章节 + 系统根据连续性账本计算的传播范围”组成。当前批次中的受影响章节失效并重过三门；传播范围跨入已经批准的前批时，只标记影响并交人工决定是否重开，不能自动修改前批正文。

依赖索引不完整时，不允许声称最小失效完全可靠。系统必须保守扩大失效范围并交人工确认。

## 10. 用户编辑与恢复

用户可以编辑：

- `course.json` 中适合表单展示的课程字段。
- `MISSION.md`、`SPEC.md`、`BLUEPRINT.md`、`RESOURCES.md`。
- 课程章节和参考资料 Markdown。
- 批次计划中的章节分配与预算。

Context Pack、质量记录、Checkpoint、工作流事件和 RC 为只读机器产物。

每次保存创建新 revision 和差异记录，不能覆盖历史。Agent 输出基于旧 revision 时不得覆盖用户的新修改。

章节正文编辑采用最小交互：用户进入 Markdown 编辑器，可切换 HTML 预览，点击“保存”后系统创建新 revision 并自动重跑受影响的质量检查。Humanizer 对人工编写内容默认只给建议，只有用户主动应用建议时才能写回。

系统区分：

- 源真值变更：可能使章节质量门和后续阶段失效。
- 元数据或索引变更：只重新构建展示和执行确定性校验，不无故重跑语言与语义门。

需要按确定性规则映射最早失效阶段的关键字段白名单：

- `audience`
- `learning_goals`
- `content_scope`
- `expected_chapter_count`
- `min_effective_chars_per_chapter`
- `token_limit`
- `source_policy`
- `resource_ids`
- `delivery_requirements`
- `acceptance_criteria`

模型只能补充风险提示，不能决定回退阶段。恢复从最早失效阶段开始，并以最近一份仍有效的已批准产物为基线，不回溯重跑无关阶段。

## 11. Token 预算

- 用户可以选择不限制 Token，或设置整课总阈值。
- 批次和章节预算是规划提示，不是内容质量验收值。
- 记录输入、输出及供应商可提供的其他 Token 类型。
- 达到总预算 80% 时提醒。
- 系统判断下一调用可能超过阈值时先暂停，让人工选择提高预算或停止。
- 模型不能提高预算，也不能用降低质量门的方式节省 Token。

## 12. 文件与数据库边界

### 12.1 PostgreSQL

数据库保存运行与流程事实，V1 最小表包括：

- `courses`
- `runs`
- `jobs`
- `artifacts`
- `review_events`
- LangGraph PostgreSQL Checkpoint 相关表

事件和可变结构优先使用 JSONB。V1 不使用 SQLite，也不引入 Redis。

### 12.2 课程工作区

```text
courses/<course-slug>/
├── course.json
├── .artifacts/
│   └── <operation-id>.<ext>
├── workspace/
│   ├── MISSION.md
│   ├── SPEC.md
│   ├── BLUEPRINT.md
│   ├── RESOURCES.md
│   ├── agent.json
│   ├── batches/
│   │   └── <batch-id>.json
│   └── context-packs/
│       └── <batch-id>/chapter-<NN>.json
├── lessons/
│   └── <NN>-<slug>.md
└── quality.json
```

文件系统保存当前可编辑内容、不可变产物版本和最终交付物；数据库保存状态、事件、引用关系、版本、审批和 Checkpoint。`.artifacts` 是默认隐藏的系统目录，工作视图仍使用稳定、可读的课程路径。

### 12.3 后台执行与恢复

FastAPI 只负责创建任务、接收人工决定和查询状态；独立 Worker 从 PostgreSQL 的 `jobs` 表领取任务并执行 LangGraph。`jobs` 只负责执行命令、租约与技术重试，不决定业务节点顺序；真实执行位置由 LangGraph Checkpoint 保存，`runs` 是供 API 和前端读取的状态投影。关键节点结束后保存 Checkpoint 和事件，人工中断时释放任务，Worker 异常退出后从最近 Checkpoint 恢复。

错误只分三类：临时网络或限流错误最多自动重试 2 次；模型输出不符合 Schema 时结构化重试 1 次；质量门失败进入内容返工循环。配置、密钥、数据库和磁盘错误直接暂停。暂停在当前模型调用结束后的安全边界生效，已产生的 Token 必须记录。

运行状态统一为 `queued`、`running`、`waiting_human`、`paused`、`failed`、`completed`、`stopped`。

## 13. 发布包

发布目录约定：

```text
releases/<course-slug>/<version>/
├── release.json
├── site/
├── markdown/
└── quality/
```

- 对外版本使用 `r0001`、`r0002` 等递增编号。
- 下载包命名为 `<course-slug>-<version>.zip`。
- 数据库内部使用 UUID。
- `release.json` 记录版本、状态、来源 revision、构建配置及所有文件的 SHA-256 清单。
- 部署适配器未来只能消费这份发布包，不从生产工作区临时拼装内容。
- 生产工作区可继续演进；已发布目录为不可变快照。

## 14. 静态站点构建

Markdown 解析、有效字符计算和 HTML 渲染统一使用 `markdown-it-py`，页面外壳使用 Jinja，代码块使用 Pygments 高亮。禁止执行 Markdown 中的原始 HTML。

发布站点不依赖 React 或服务端运行，CSS 和少量阅读交互 JavaScript 随发布包交付，不使用外部 CDN。构建至少生成课程首页、逐章 HTML、样式与脚本；原始 Markdown 单独复制到下载目录。渲染器、模板和静态资源版本全部进入 `release.json` 哈希清单，生成后的 HTML 不允许人工编辑。

## 15. Skill、提示词与模型边界

### 15.1 V1 Skills

V1 只保留两个通用 Skill：

- `instructional-writer`：教学内容组织、讲解、示例、练习与局部修订方法。
- `natural-language-editor`：自然中文诊断与局部表达优化方法。

语义审校属于课程业务节点，不做成 Skill。

Skill 不包含业务实体、工作流状态、输出 Schema、评分阈值、文件路径和存储协议。业务要求由节点提示词和 Context Pack 注入；输出 Schema、状态、哈希和路由由系统代码管理。

社区 Skill 仅作为设计和评测参考。生产使用前必须本地化、版本锁定、人工审查并通过固定测试集，不在运行时远程加载第三方 Skill。

### 15.2 提示词

提示词以代码仓库中的 Markdown 文件维护，不建设独立管理系统。每次模型调用记录提示词名称和实际内容哈希。提示词修改只影响后续调用；被重开的章节使用当时最新版本并记录新哈希。

### 15.3 模型

V1 配置一个全局默认模型，节点允许可选 `model_override`。前端只提供简单的默认模型设置，不展示复杂节点调度。V1 先支持 OpenAI 兼容接口，内部保留薄适配层。

每次调用记录实际供应商、模型、参数、Skill 版本、提示词哈希、输入输出哈希和 Token 用量。

模型服务地址、默认模型和 API Key 通过服务端环境变量配置。API Key 不进入数据库、课程文件、Checkpoint、日志或前端。前端只能显示模型名称、服务地址和是否已配置，并可发起连接测试。V1 修改配置后重启服务生效。

## 16. 前端范围

### 16.1 课程库

展示课程列表、当前阶段、运行状态、最近更新时间和发布状态，可创建课程、继续生成、进入阅读或归档。归档前必须先停止仍在运行的任务；归档不删除数据库、工作区和发布版本，可随时取消归档。

### 16.2 生成工作台

采用三栏布局：

- 左侧：七阶段导航及状态。
- 中间：当前产物、章节、批次或质量详情。
- 右侧：审核信息、风险和人工操作。
- 顶部：课程状态、Token 预算、暂停和编辑入口。

节点日志和 Token 明细默认折叠。工作台以表单、产物和审核决定为核心，不设计成聊天界面。

前端使用状态轮询而非 SSE。工作台在运行期间约每 2–3 秒查询一次，课程列表约每 10 秒查询一次；页面进入后台或任务离开运行态后降低或停止高频轮询。不向前端流式展示模型正文。

进入 `waiting_human` 时，在顶部、阶段导航和课程列表显示“待你确认”。V1 只有应用内提醒，不做外部通知。

### 16.3 课程阅读页

提供简洁的长文阅读体验，包括课程目录、模块分组、章节阅读、阅读进度、上一章/下一章和 Markdown 下载。阅读页不展示 Agent 生产日志。

视觉方向采用浅蓝白色主题。产品正式名称为“课程生成器”。

## 17. V1 验收标准

- 用户能通过表单创建课程，并完成七阶段流程。
- 流程可以在人工中断点暂停，并从 PostgreSQL Checkpoint 恢复。
- 用户 URL、粘贴资料及联网资料均能形成可追溯快照。
- 每章由单独模型调用生成，并按批次串行完成三门质量闭环。
- 自动返工不会超过约定轮数，连续失败能升级人工。
- 人工编辑不会被基于旧 revision 的模型结果覆盖。
- 所有质量结果均绑定正文或事实源哈希，失效可以确定性判定。
- 全课程通过阶段六后可生成不可变 RC。
- 发布操作不改变 RC 文件，只提升状态。
- 发布包包含静态 HTML 站点、Markdown、质量报告和完整哈希清单。
- 用户可以在课程阅读页正常阅读并下载 Markdown。
- Worker 异常退出后能够从最近 Checkpoint 恢复，人工等待状态不会占用执行任务。
- 未配置搜索 Key 时仍可使用用户 URL 和粘贴文本；配置后可自动搜索并抓取来源快照。
- 课程可以归档和恢复显示，但不能从界面永久删除。
- 工作台可以通过轮询及时显示运行、失败、完成和等待人工状态。

## 18. 需求基线状态

V1 核心需求已形成基线，产品正式名称确定为“课程生成器”。品牌标识采用浅蓝色圆角方块与白色“课”字，不扩展复杂视觉系统。当前不存在阻塞架构设计和开发的未决产品事项。
