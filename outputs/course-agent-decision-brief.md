# 课程生成器：决策摘要与交接说明

> 更新日期：2026-09-07  
> 用途：供后续参与者快速了解项目，不是对话记录。  
> 产品名称：课程生成器。品牌标识为浅蓝色圆角方块与白色“课”字。

## 1. 一句话定义

面向个人自学者的课程生成系统：把需求确认、资料收集、课程规划、逐章写作、质量审校、人工返工和发布固化为可暂停、可恢复、可追溯的工作流，最终交付 Markdown 课程、静态 HTML 站点和质量报告。

## 2. 已确认的总体方向

- 后端：FastAPI。
- 前端：React。
- 工作流：LangGraph + PostgreSQL Checkpoint。
- V1：本地单实例，不做登录和多人协作。
- 用户主要通过表单、产物和审核界面操作，不做聊天优先产品。
- 课程正文唯一事实源是 Markdown；HTML 只是从 Markdown 构建的发布视图。
- 系统代码控制流程、权限、质量门、预算、暂停和恢复；模型只负责理解、规划、写作、语言优化和审校。
- 人工在关键节点拥有批准、要求返工、停止三种权力；最终发布决定永远由人工作出。
- 每个重要产物都持久化，每次人工决定可恢复，每次模型调用和 Token 都可追溯。

## 3. 七个用户可见阶段

七阶段是前端进度与审批视图，不等于 LangGraph 只有七个节点，也不强制对应七个子图。V1 使用一个相对平坦的主图，仅将阶段五、六复用的单章生产/修复循环实现为子图。

1. **课程需求**：收集课程名称、受众、学习目标、范围、期望章节数、单章有效字符下限、Token 限制、来源政策和补充资料。
2. **任务定义**：形成可验收任务，产出 `MISSION.md` 和 `SPEC.md`。
3. **来源与蓝图**：处理用户资料、按政策联网搜索并形成 `RESOURCES.md`、`BLUEPRINT.md` 和章节来源依赖。
4. **批次规划**：沿模块边界划分批次，登记章节、顺序、预算和 Context Pack 引用范围。
5. **批次生产**：逐章生成、Humanizer、语义审校和有界返工；批内全部通过后才算交付。
6. **整课质量闭环**：检查整课事实、教学、术语、先修关系和跨章一致性，并按影响范围修复。
7. **整课确认与发布**：生成不可变 RC，经人工确认后提升为正式发布。

## 4. 阶段四与阶段五的关键边界

- 批次规模按批配置，超大章节可以单独成批。
- V1 默认顺序执行。只有依赖信息足以确定不存在内容依赖时才允许并行；不确定就顺序执行。
- 规划阶段的章节体量只来自蓝图目标或估算，不能代替阶段五的真实有效字符验收。
- 阶段四只保存批次计划和可解析的 `context_pack_scope`，禁止生成 Context Pack 文件。
- Context Pack 统一在阶段五、实际生成章节前创建，避免蓝图调整后残留无效副本。
- 阶段四退出校验只做章节覆盖、顺序、模块边界、预算级可行性、范围引用完整和“尚未生成 Context Pack”检查，不做内容质量验收。

## 5. 单章生产闭环

```text
生成 Context Pack
→ 首次正文生成或定向修复
→ 确定性预检
→ Humanizer
→ 确定性回归
→ 语义审校
→ 三门汇总
```

规则：

- 一次正文生成调用只写一章；一个批次包含多次串行调用。
- 预检失败直接回到写入或修复步骤，不调用 Humanizer 和语义审校。
- 语义审校要求修改正文后，修改内容必须重新经过 Humanizer 和确定性回归。
- Humanizer 只处理变化的散文；纯结构变化或散文哈希不变时 no-op，并沿用原语言结果。
- 三门失败证据统一进入下一轮修复输入。
- 通过后冻结的是当前批次通过质量门的 Markdown 版本；后续出现新证据或人工发起时仍可重开，重开后重跑受影响质量门。

### 自动返工上限

- 一轮是“一份候选正文走到完整质量门汇总”，不是单次模型调用。
- 每章最多 3 轮自动生成或定向修复。
- 同一 blocker 指纹连续出现 2 轮时提前转人工。
- 各轮出现不同问题但累计 3 轮仍失败时转人工。
- 指纹由规则、逻辑位置和证据版本哈希组成。
- 网络重试不计入正文返工轮数。
- 人工提供新的定向意见或证据后可以重置自动计数，但历史保留。
- 内层单章任务上限与外层整课闭环总闸分开管理。

## 6. 三个质量门

所有质量记录均绑定 `{gate, hash, revision}`；哈希不匹配即失效。

### 确定性门

由代码检查 Markdown 结构、必要元素、引用格式、有效字符数、来源引用可解析性和构建可用性。

有效字符使用 Markdown AST 计算可见正文：中英文字母和数字计入；标点、空白、Markdown 语法、URL、代码块和章末来源表不计；链接标签计入；正文引用块计入。Humanizer 后重新计算，最终结果绑定语义审校通过的正文哈希。字符达标只代表篇幅通过，重复填充由语义门处理。

### 语言门

Humanizer 业务节点是唯一语言门。四个等权维度为自然度、清晰度、简洁度和具体教学感：每维不低于 85，综合分不低于 90，且没有语言 blocker 才能通过。

评分必须由行为锚点映射，并为扣分和 blocker 提供具体片段、位置、原因和修复方向。语言 blocker 独立于分数，包括提示词残留、机械模板句、严重翻译腔或表达断裂、重复填充、表达影响理解、虚构个人身份或感受造成不可信感。事实性虚构只归语义门，避免双罚。

### 语义门

不设置数字总分，四维分别输出 pass、warning 或 blocker：事实与来源、目标与范围、教学有效性、逻辑与连续性。

- 目标与范围只判断覆盖和排除；教学有效性只判断讲解和证据质量。
- 同一缺陷不得在两个维度重复登记。
- 本章内部一致性问题属于本章 blocker。
- 跨章矛盾只作为 warning 进入连续性记录，由批次或整课审查决定是否重开其他章节。
- 审校只读，不直接修改正文；“内容正确但表达影响理解”可提供回到 Humanizer 的建议，路由仍由系统决定。

## 7. 整课修复与人工权力边界

- 根因清晰、只影响单章且不涉及结构、政策或传播范围的问题，可进入有界自动返工。
- 跨章、多章或根因不明的问题，先生成修复计划交人工确认。
- 修复计划必须包含根因、目标章节及顺序、传播范围、需要重跑的门。
- 计划确认后，各章自动进入自己的有界返工，不再逐章卡人工，除非达到预算或错误上限。
- 修复计划只有“验证通过”或“人工证据证明问题不成立”两种合法关闭方式。
- 人工不能在批准界面直接豁免真实 blocker；规则修改必须走受控变更并进入审计。
- 人工要求返工时，影响范围为人工指定章节加系统根据连续性账本推导的传播范围。
- 传播进入已批准前批时只标记影响，由人工决定是否重开，不能自动修改前批正文。
- 未解决 warning 的人工知悉必须和进入阶段七的确认动作绑定并记录。

## 8. 来源与联网搜索

用户可提供网页 URL 或粘贴文本。来源政策有四种：

- 用户资料 + 官方资料。
- 仅内部材料。
- 仅公开官方资料。
- 扩展资料并交叉核验。

来源政策允许时，系统在阶段三自动联网搜索，用户在阶段三统一审核，不逐次请求授权。搜索结果只作为候选；必须抓取实际页面、形成正文快照并满足来源政策，才能进入 Context Pack。

V1 采用轻量方案：保存原始快照和哈希，按标题和段落简单切分，建立章节到片段的映射；不使用向量数据库。用户主动刷新 URL 时才生成新版本，不自动监控网页变化。抓取失败可重试、删除或改用粘贴文本。

实现采用 Tavily 发现 URL、HTTPX 抓取页面、Trafilatura 提取正文。Tavily Key 可选；未配置时自动搜索关闭，但用户 URL 和粘贴文本仍可使用。

抓取服务只允许 HTTP/HTTPS，禁止访问本机和内网地址，并设置大小和超时限制。

## 9. Context Pack

Context Pack 是系统根据已批准产物确定性组装的单章只读输入，不是模型自由总结出的上下文。

每章只包含本章目标、蓝图、允许来源片段、必要的前文摘要和术语、写作约束。阶段五保存当前版本：

```text
workspace/context-packs/<batch-id>/chapter-<NN>.json
```

蓝图或来源变化时旧版本失效。定向返工基于原 Context Pack 追加当前正文和质量证据，不为每次调用复制整份文件。

模型输入按以下顺序由系统拼装：

```text
通用模型约束
+ 可选通用 Skill
+ 节点业务提示词
+ Context Pack
+ 代码指定的输出 Schema
```

## 10. Skill、提示词和模型

V1 只有两个通用 Skill：

- `instructional-writer`：通用教学写作和局部修订方法。
- `natural-language-editor`：自然中文诊断和局部改写方法。

Skill 不包含课程 ID、章节 ID、阶段、批次、Schema、哈希、评分阈值、重试、文件或数据库协议。所有业务要求由节点提示词和 Context Pack 注入；输出结构、版本、质量门和路由由业务代码负责。语义审校高度依赖课程业务规则，V1 不做成 Skill。

社区 Skill 只作为设计与评测参考；生产前必须本地化、版本锁定、人工审查并通过测试，不在运行时直接加载第三方 Skill。

提示词作为仓库内 `.md` 文件维护。调用时记录提示词名称和内容哈希，不建设 Prompt 管理后台。

V1 使用一个全局默认模型，节点可选覆盖；先支持 OpenAI 兼容接口。每次调用记录实际模型、参数、Skill 版本、提示词哈希、输入输出哈希和 Token。

模型地址、名称和 API Key 通过服务端环境变量配置；密钥不进入数据库、文件、Checkpoint、日志或前端。V1 修改配置后重启服务。

## 11. 数据、文件和发布

PostgreSQL 保存流程事实：`courses`、`runs`、`jobs`、`artifacts`、`review_events` 和 LangGraph Checkpoint。`jobs` 负责 Worker 调度、租约与技术重试，不保存业务执行游标；Checkpoint 是真实执行位置，`runs` 是状态投影。文件系统保存当前可编辑内容、不可变产物版本和最终交付物。V1 不使用 SQLite，也暂不引入 Redis。

精简工作区：

```text
courses/<slug>/
├── course.json
├── .artifacts/<operation-id>.<ext>
├── workspace/
│   ├── MISSION.md
│   ├── SPEC.md
│   ├── BLUEPRINT.md
│   ├── RESOURCES.md
│   ├── agent.json
│   ├── batches/<batch-id>.json
│   └── context-packs/<batch-id>/chapter-<NN>.json
├── lessons/<NN>-<slug>.md
└── quality.json
```

发布包：

```text
releases/<slug>/<version>/
├── release.json
├── site/
├── markdown/
└── quality/
```

对外版本使用 `r0001` 等递增编号，下载包命名为 `<slug>-<version>.zip`。RC 是完整、不可变的候选包；`release.json` 记录全部输入和文件哈希。发布只提升状态，不改变 RC 字节。生产工作区可以继续变化，已发布快照不能修改。

## 12. 编辑、失效与恢复

- 用户可编辑课程表单字段、MISSION、SPEC、BLUEPRINT、RESOURCES、章节 Markdown 和批次计划。
- Context Pack、质量记录、Checkpoint、事件和 RC 为只读机器产物。
- 每次保存创建新 revision 和差异，旧版本不覆盖。
- 基于旧 revision 的模型结果不能覆盖用户新修改。
- 系统区分源真值变更和纯元数据/索引变更，避免修改标题就让全部章节重跑质量门。
- 章节到来源文件的依赖索引必须先可信，才能执行最小失效；索引不完整时保守扩大并交人工确认。
- 回退阶段由确定性规则判断，模型只能提供风险提示。
- 恢复从最早失效阶段开始，以最近仍有效的已批准产物为基线，不重跑无关阶段。
- RC 任一绑定事实源变化即失效；重新构建全站并做全量确定性检查，语言与语义门只对真正失效章节重跑。

章节编辑界面只保留 Markdown 编辑、预览和保存。保存自动创建 revision 并重跑受影响检查；Humanizer 对人工文字默认只给建议，用户主动应用后才写回。

## 13. 前端范围

- 课程库：课程列表、阶段、运行状态和发布状态。
- 生成工作台：左侧阶段导航、中间产物、右侧审核，顶部显示状态、Token 和暂停操作。
- 课程阅读页：目录、模块、章节、阅读进度、上下章和 Markdown 下载。

V1 使用状态轮询而非 SSE，不流式展示模型正文。运行中的工作台约每 2–3 秒轮询，课程列表约每 10 秒轮询；等待人工、失败或完成时显示应用内徽标和提示，不发送外部通知。

课程支持归档和取消归档，不提供界面永久删除或工作区导入。对外交付使用发布包下载。

界面采用浅蓝白色主题。节点日志和 Token 明细默认折叠。产品名称统一使用“课程生成器”。

## 14. 后台执行与构建选型

FastAPI 接收请求，独立 Worker 从 PostgreSQL 领取任务并执行 LangGraph。人工等待释放 Worker；进程异常后从最近 Checkpoint 恢复。临时错误最多重试 2 次，Schema 错误结构化重试 1 次，质量失败走内容返工循环。

Markdown 解析、有效字符计算和 HTML 渲染统一使用 `markdown-it-py`；Jinja 生成页面外壳，Pygments 负责代码高亮。静态站点不依赖 React、服务端或外部 CDN，生成后的 HTML 不允许手工修改。

## 15. 已确认的技术实现方向

- 单仓库：`backend`、`frontend`、`skills`、`courses`、`releases`、`docs`。
- 后端先完整实现，随后开发 React 前端，最后统一联调验收。
- FastAPI 采用独立 Worker；Worker 从 PostgreSQL `jobs` 表领取任务。
- LangGraph 使用一个主图和一个可复用的 `chapter_cycle` 子图。
- Graph State 只保存运行标识、当前作用域和产物引用，不保存正文或完整模型对话。
- 产物使用稳定 `operation_id`、临时文件加原子替换和 SHA-256，实现节点幂等与崩溃恢复。
- 前端采用 React、TypeScript、Vite、React Router 和 TanStack Query，不引入全局状态库。
- 后端采用 Python 3.12 同步实现、SQLAlchemy、Psycopg、Alembic、LangGraph PostgreSQL Checkpointer 和 OpenAI-compatible SDK。

## 16. 后续继续方式

V1 核心需求、产品名称和技术设计均已形成基线，后续不应重新讨论已冻结规则，除非出现新需求或实现证据。开发时以技术设计文档为实现入口。

仍应坚持“一次只确认一个重要问题；普通实现细节采用合理默认值，不做过度设计”。
